# 最小 LED 警示鏈架構

## 模組責任

- `TFMiniPlusSerialDevice` 單獨擁有 UART（Universal Asynchronous Receiver-Transmitter／通用非同步收發傳輸器）連線，並只負責生命週期與讀取。
- `TFMiniPlusParser` 只接收位元組、驗證 9-byte frame 並建立 `TFMiniPlusMeasurement`，不依賴 UART 或 GPIO。
- `WarningPolicy` 只驗證量測與回傳 `WarningState`，不執行 I/O。
- `WarningController` 將單筆量測交給 policy，再把結果交給注入的 `LedDriver`。
- `WarningPipeline` 協調一次裝置讀取；空讀取會輸出 `SENSOR_FAULT`，不會被當成安全。
- `ThreeColorLedDriver` 將狀態映射為三個數位輸出，不直接依賴任何 GPIO 套件。
- `GpioZeroDigitalOutput` 是實體 adapter，以 `gpiozero.OutputDevice` 控制輸出，並明確建立 `LGPIOFactory(chip=0)`，不依賴 gpiozero 自動選擇 backend。

## 距離規則

預設合理範圍上限依 TFMini Plus 的 12 m 量測範圍設定，集中於 `DistanceThresholds`：

- 小於 1.5 m 且大於 0：`DANGER`（危險），紅燈。
- 1.5 m 至 3.0 m（含兩端）：`WARNING`（警戒），黃燈。
- 大於 3.0 m 且不超過 12.0 m：`SAFE`（安全），綠燈。
- 缺失、非數值、非有限值、零、負值或超過 12.0 m：`SENSOR_FAULT`（感測器故障），紅燈與黃燈同亮。

門檻可透過建立不同的 `DistanceThresholds` 覆寫，不需要修改 policy 程式碼。

## 無硬體測試

執行 `pytest`。測試使用 fake serial factory、fake digital output 與 fake LED driver，涵蓋 parser、UART 裝置層、所有距離邊界、故障資料，以及從有效 UART frame 到 LED 狀態的完整路徑。

一般開發與純軟體測試只需安裝 core 與 `dev` extra，不會安裝 gpiozero 或 lgpio：

```bash
python -m pip install -e ".[dev]"
```

Raspberry Pi 硬體環境則另外安裝 `hardware` extra：

```bash
python -m pip install -e ".[dev,hardware]"
```

## 實體 adapter 與資源生命週期

`LedPins.raspberry_pi_default()` 集中保存目前接線：紅燈 BCM GPIO17（實體針腳 11）、黃燈 BCM GPIO27（實體針腳 13）、綠燈 BCM GPIO22（實體針腳 15）。三者皆為 active high，建立 `OutputDevice` 時使用 `initial_value=False`。各 GPIO 經獨立限流電阻連 LED 正極，LED 負極接 GND。

實體 adapter 擁有三個 `OutputDevice` 與共用的 lgpio pin factory。建立中途失敗、明確 `close()` 或 context manager 離開時，會盡力先關閉全部 LED，再關閉各 device 與 factory。另註冊 process-exit 清理作為正常程式結束的安全網；呼叫 `close()` 後不得再次寫入。

## LED 診斷 CLI

`led-diagnostic` 依序顯示紅、黃、綠與 `SENSOR_FAULT`（紅黃同亮）。缺少 `--confirm-hardware` 時會以 usage error 結束，且不建立 GPIO adapter。實機執行範例：

```bash
led-diagnostic --confirm-hardware --step-seconds 1
```

執行前仍須依專案規範確認指令、接線、預期效果及 GPIO 切換風險，並確保沒有其他程序使用這三個 GPIO。CLI 在完成、例外與 `Ctrl+C` 後都會關閉輸出並釋放資源。pytest 僅注入 fake output、fake device factory 與 fake pin factory，不會存取 `/dev/gpiochip*`。

## TFMini Plus 至實體 LED 整合診斷

`rear-warning-diagnostic` 使用完整的 headless 資料流：

```text
/dev/ttyAMA0
  -> TFMiniPlusSerialDevice
  -> TFMiniPlusParser
  -> TFMiniPlusMeasurement
  -> WarningPolicy
  -> WarningController
  -> ThreeColorLedDriver
  -> GpioZeroDigitalOutput
  -> 紅／黃／綠 LED
```

CLI 僅組合既有模組，不重新實作距離門檻。參數包含 `--port`、`--baudrate`、`--timeout`、`--duration`、`--max-samples`、`--red-pin`、`--yellow-pin`、`--green-pin`、`--gpio-chip` 與 `--confirm-hardware`。必須設定 `--duration` 或 `--max-samples`，不允許預設無限執行。

未提供 `--confirm-hardware` 時，只顯示 UART、GPIO、LED 對應及 `DistanceThresholds` 設定，不建立 serial device、不建立 `GpioZeroDigitalOutput`，因此不會開啟 UART、claim GPIO 或改變 LED。確認後先建立明確的 `LGPIOFactory(chip=...)` 與三個 output、確保全關，再開啟 UART。程式環境亦建議設定 `GPIOZERO_PIN_FACTORY=lgpio`，使其他 gpiozero 工具維持相同 backend。

`rear_warning.outputs` 只匯出硬體無關介面；gpiozero/lgpio 只會在 CLI 完成參數解析且通過 `--confirm-hardware` 後 lazy-load。若沒有安裝 `hardware` extra，CLI 會以非零狀態結束並提示 `pip install -e ".[hardware]"`，不會輸出難以理解的 import traceback。

診斷 session 的初始邏輯狀態是 `SENSOR_FAULT`，因為此時尚無有效距離可證明安全；但 GPIO 建立後仍保持三燈全關，不會在程式啟動瞬間點亮故障燈。第一筆有效量測才由既有 `WarningPolicy` 決定並顯示 SAFE、WARNING 或 DANGER，同時記錄例如 `SENSOR_FAULT -> SAFE` 的首次轉換。若第一筆讀取是 timeout／empty read，才實際顯示紅黃同亮的 `SENSOR_FAULT`，且不把相同狀態誤計為轉換。

UART 空讀、不完整 frame 以及只有無效 checksum frame 的讀取，會由既有 serial/parser 邊界回傳空 measurement list，整合 CLI 交給 `WarningController.process(None)` 顯示 `SENSOR_FAULT`。Parser 意外例外會記入 `parser_errors`、顯示 `SENSOR_FAULT` 並結束；serial exception 會明確輸出 UART 錯誤、嘗試顯示 `SENSOR_FAULT` 並結束。GPIO 寫入錯誤也會被記錄，所有情況最後都嘗試關閉 UART 與 GPIO。只有兩者皆成功關閉時摘要才會顯示 `cleanup_completed=true`。

任何 UART、LED device 或 lgpio factory cleanup failure 都會令診斷回傳非零狀態。主要執行錯誤與每一項 cleanup error 會分別保留，不能以清理錯誤掩蓋原始問題。只有 `cleanup_completed=true` 且 exit code 為 0 才可認定整合診斷完整成功；`led-diagnostic` 也只會在 cleanup 成功後印出完成訊息。

`tfmini.service` 可能已占用 `/dev/ttyAMA0`。確認停止服務不會影響其他工作後，可由使用者手動執行以下範例；Codex 與 pytest 不會自行執行：

```bash
sudo systemctl stop tfmini.service

GPIOZERO_PIN_FACTORY=lgpio rear-warning-diagnostic \
  --port /dev/ttyAMA0 \
  --baudrate 115200 \
  --timeout 0.1 \
  --duration 10 \
  --confirm-hardware

sudo systemctl start tfmini.service
```

### 門檻附近狀態抖動

實測觀察到距離在現有離散門檻附近來回變動時，狀態會相鄰切換：

- 3.00 m／3.01 m 附近會在 `WARNING` 與 `SAFE` 之間切換。
- 1.49 m／1.50 m 附近會在 `DANGER` 與 `WARNING` 之間切換。

這是未經濾波的原始距離直接套用目前門檻時可預期的邊界行為，不代表 parser 或 GPIO 錯誤。本次僅記錄現象，不修改既有距離門檻，也不在此階段改變警示策略。

後續工作應評估距離濾波及／或 hysteresis（遲滯）策略，並先定義延遲、穩定性與安全失效行為，再以獨立測試驗證門檻切換。本次任務未實作濾波或 hysteresis。
