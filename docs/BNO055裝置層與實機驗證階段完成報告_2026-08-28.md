# BNO055 裝置層與實機驗證階段完成報告

日期：2026-08-28

## 1. 階段目標

本階段建立獨立、headless、可測試的 BNO055 軟體裝置層，確認 Raspberry Pi 5
上的 GY-BNO055 身分與 I2C 通訊，安全控制 CONFIGMODE／NDOF 生命週期，並以
有限時間的靜止桌面診斷驗證 startup data-quality gate 與 cleanup。

本報告只宣告此裝置層與限定實機驗證階段完成，不宣告 BNO055 子系統、車輛
動態融合或整體專題完成。

## 2. 硬體與接線

- 主機：Raspberry Pi 5 Model B。
- 模組：GY-BNO055，使用 3.3 V 供電。
- VIN → Raspberry Pi 3.3 V。
- GND → GND。
- SCL/Rx → GPIO3／SCL1。
- SDA/Tx → GPIO2／SDA1。
- ADD、INT、BOOT、REST 未連接。
- 實機測試期間模組固定、平放、保持靜止且不接觸導電物。

## 3. I2C 啟用、位址與識別

Raspberry Pi I2C 已啟用，GPIO2／GPIO3 使用 `/dev/i2c-1`。限定掃描確認唯一
位址為 `0x29`，未掃描或操作 `i2c-13`、`i2c-14`。固定身分暫存器為：

| 欄位 | 值 |
| --- | --- |
| CHIP ID | `0xa0` |
| Accelerometer ID | `0xfb` |
| Magnetometer ID | `0x32` |
| Gyroscope ID | `0x0f` |

20 次唯讀 ID 讀取全部一致，`ST_RESULT=0x0f`，沒有 I2C error。初始模式為
CONFIGMODE（`OPR_MODE=0x00`）；進入融合前曾觀察到 `SYS_ERR=0x09`，此值不被
解讀為 NDOF 成功或失敗。

## 4. 軟體分層架構

```text
optional smbus2 SMBus
  → SMBusRegisterIO
  → BNO055Device
  → register conversion functions
  → frozen/slotted measurement models
  → I/O-free measurement quality assessment
  → confirmation-gated bno055-diagnostic CLI
```

BNO055 stack 與 TFMini Plus、WarningPolicy、hysteresis、WarningController、UART
及 LED modules 分離。本階段沒有把姿態或加速度接入警示決策。

## 5. 元件職責

- Identity：保存位址、四個固定 ID、software revision 與 bootloader revision。
- Device：封裝 register I/O、身分驗證、模式初始化、readiness、量測交易及 cleanup。
- Register conversion：純函式處理 signed little-endian、offset、calibration bits
  與 datasheet scaling，不執行 I/O。
- SMBus adapter：精確轉送 bus、address、register、value 與 block length；明確
  close，例外不被吞掉。
- CLI：解析有界參數、列出寫入計畫、要求 `--confirm-hardware`、統計結果並
  保留 primary／cleanup failures。

## 6. Lazy import 與 optional hardware dependency

`smbus2` 只宣告於 `hardware` optional extra，與既有 `gpiozero`、`lgpio` 一樣
不屬於核心必要依賴。核心、models、register conversions、device、quality 與
未確認 CLI imports 都不 eager-load `smbus2`、`gpiozero` 或 `lgpio`。只有使用者
提供硬體確認後，hardware loader 才載入 SMBus adapter。

## 7. 模式生命週期

確認身分後依序執行：

```text
CONFIGMODE → page 0 → normal power → default SI/degree units → NDOF
→ bounded diagnostic → CONFIGMODE → close bus
```

CONFIGMODE 與 NDOF mode switch 分別保留 19 ms 與 7 ms 最低等待。若身分尚未
確認，不會寫入 CONFIGMODE；若初始化已開始，任何正常、錯誤或 Ctrl+C 路徑
都會嘗試回到 CONFIGMODE並關閉 bus。

## 8. Readiness polling

NDOF 後只在 mode/status/error 為 `0x0c/0x05/0x00` 時成功。非零 `SYS_ERR` 或
system-error status 立即失敗；I2C exception 不會被改寫為 timeout。Polling
同時使用 monotonic deadline 與由 `ceil(timeout / interval) + 1` 推導的最大
次數，因此 clock 停滯或倒退、sleep no-op 也不會無限迴圈。Readiness timeout
保留最後 mode/status/error，且失敗後仍 cleanup。

## 9. Runtime 狀態驗證

每筆 measurement 都檢查 operation mode、system status 與 system error。
非 `0x0c/0x05/0x00` 的當筆不輸出、不計數，CLI 立即非零結束。Measurement
保存的三個狀態值就是同一組被驗證的交易值，不會另讀第二組造成記錄不一致。

## 10. 26-byte measurement block

每筆量測只從 `0x1a` 執行一次 length 26 block read，完整覆蓋 `0x1a–0x33`。
同一 block 解析 Euler、quaternion、linear acceleration 與 gravity；之後依序
讀取 temperature `0x34`、calibration `0x35`、operation mode `0x3d`、system
status `0x39`、system error `0x3a`。Offsets、little-endian、正負 fixture 與
scaling 均由 fake-bus tests 鎖定。

## 11. Startup quality gate

Readiness 成功後、正式 sampling 前，data-ready 階段檢查所有浮點值 finite、
quaternion norm `0.5–1.5`、gravity norm `5–15 m/s²`，並再次要求狀態為
`0x0c/0x05/0x00`。這些是寬鬆的資料完整性門檻，不要求 Euler 或 linear
acceleration 非零，也不要求 calibration 為 3。

預設 timeout 為 2.0 秒、interval 為 0.02 秒、最大嘗試 101 次，同時受 deadline
與 poll count 限制。狀態正常但資料未就緒的 startup frame 只增加 discard
counter，不輸出、不計入 valid count 或 rate。第一筆合理資料成為 sample 1，
sampling duration 從此刻開始。正式 sampling 後再出現資料品質錯誤則立即失敗。

## 13. 自動化測試

本階段完整 suite 為 367 項，涵蓋 register conversion、身分、初始化各階段、
readiness sequence／timeout、constant／backward clock、partial cleanup、26-byte
transaction order、SMBus forwarding、startup quality、runtime data failure、
Ctrl+C、時間統計與未確認 CLI 零 I/O。所有測試使用 pure fixture、fake bus 或
fake clock，不接觸實體硬體。

## 14. 安全清理與錯誤處理

- 身分驗證失敗時只關閉 bus，不寫 CONFIGMODE。
- 初始化部分成功後，錯誤路徑仍嘗試 CONFIGMODE cleanup 與 bus close。
- Primary error 與一個或多個 cleanup error 都會被保留。
- Readiness、data-ready、runtime state/data、I2C、Ctrl+C、零樣本及 cleanup
  failure 都有明確非成功行為；Ctrl+C 在 cleanup 成功時回傳 130。
- Sampling elapsed 不含 cleanup；total elapsed 包含初始化、sampling 與 cleanup。
- 正常測試後另以一次唯讀 `OPR_MODE` 確認兩次均為 `0x00`。

## 16. 階段邊界

### 本階段已完成

- I2C 啟用與裝置識別。
- BNO055 軟體裝置層。
- NDOF 模式控制。
- 靜止桌面環境的 bounded diagnostic。
- Startup data-quality gate。
- 實體 NDOF 回歸。
- 安全 cleanup。

### 尚未完成

- 完整四項 calibration。
- 校正資料保存／恢復。
- 車輛或道路動態測試。
- 急加速、急減速、傾斜、轉彎、震動分析。
- BNO055 與 TFMini Plus 的時間同步。
- BNO055 接入 WarningPolicy。
- 依車輛運動狀態調整警示。
- 長時間穩定性測試。
- systemd 正式執行整合。

## 17. 下一階段建議

1. 先設計不寫入敏感校正資料的四項 calibration 觀察流程，再另案審查保存／
   恢復策略與風險。
2. 建立有界、可重現的動態 fixture 與實機測試矩陣，涵蓋加減速、傾斜、轉彎
   與震動，但先保持 BNO055 不影響 WarningPolicy。
3. 定義 BNO055／TFMini Plus timestamp、sampling rate、延遲與資料 freshness
   契約，再考慮 sensor fusion。
4. 以 fail-safe policy review 決定運動狀態如何影響警示，完成軟體與實機驗證
   後才接入正式 service。

在上述工作完成前，不應宣稱 BNO055 子系統或整體智慧後方接近警示專題已全部
