## LED 逐筆映射核對

以 SHADOW 與 LED assessment 的原序列一對一比對：

- 3,572/3,572 timestamp 相同。
- 對每筆都重算：NO_TARGETS → 全關；fault availability → 紅+黃；coalesced →
  保持；applied selected → 現行 stabilized state 的 SAFE/綠、WARNING/黃、
  DANGER/紅、SENSOR_FAULT/紅+黃。
- 實際 `gpio_pattern` 與預期 pattern 不符：0。
- `gpio_write_applied` 與「預期 pattern 是否相對前一 pattern 改變」不符：0。

Assessment 期間實際有 100 次 pattern 改變：

| 直接分類 | 次數 |
| --- | ---: |
| 不同 ID switch 且 state 改變 | 56 |
| 同 ID 跨門檻／遲滯 | 39 |
| NO_TARGETS 全關 | 2 |
| NO_TARGETS 後重新取得 | 2 |
| 開始後第一次顯示 | 1 |

其中 140 次 ID switch 有 56 次改變燈號，其餘 84 次新舊目標仍落在同一
stabilized state，所以沒有寫新 pattern。assessment 變燈間隔中位數 0.857 s，
55/99 個間隔小於 1 s，29/99 小於 0.5 s，最短 0.048 s。因此記錄支持
操作員所述「反覆改變」，不是單純的終端顯示錯覺。

最後 cleanup 又將當時亮燈 pattern 改成全關，所以連同收尾共有 101 次
實際 pattern 改變。Startup 也主動寫全關，但它是安全初始化，不是由一個
已知亮燈 pattern 轉成另一 pattern。

此核對證明程式記錄的每次變燈都符合當時 selected distance 與
`distance_warning_stabilized`。它無法取代操作員對 A/B 兩顆同色實體燈的
逐次目視；本輪沒有這種逐次目視紀錄。

## 環境影響：支持證據與未知

### 已證實

1. 這輪不是 UART/parser 壞包所造成：checksum、sync discard、trailing、time
   discontinuity 全為 0，也沒有 runtime I/O error。
2. selector 每一個完整有效週期都選當期最近 candidate。
3. 跳動由多個可同時成立的現象組成：近 candidate 消失、另一 ID 出現或變得
   更近、同 ID 距離跨過門檻，以及 6 次 ID-switch reset 改變了原本會保留的
   遲滯狀態。
4. 多目標很頻繁：88.5% 的 selected assessments 有至少 2 個 candidates，25.6%
   有至少 4 個。
5. 候選距離有明顯重複群：約 2.8 m（953 次）、4.6 m（641）、4.7 m（557）、
   6.4–6.5 m（分別 321/372）、7.5–7.6 m（分別 273/242）。1,816/3,569 個 applied
   cycles 有至少一個 `>=6 m` candidate，其中 1,720 個同時選中 `<3 m`
   的較近目標。這些記錄與同一觀測區存在多個反射來源相容。

### 仍未知／不能宣稱

1. Radar ID 不是持續物理身分，無法將某 ID 宣稱為特定家具、特定牆壁或
   操作員。
2. 沒有 operator stage events、室內平面圖、已知反射物位置、空場基準、雷達視野／
   旁瓣實測或目標真值，不能把上述距離群直接命名為家具或牆。
3. 多目標可能來自家具／牆壁、其他人或物、多徑／旁瓣、安裝角度或實際人員
   動作；本 capture 無法在這些原因中唯一定因。
4. 已證實的是軟體輸出記錄符合規則，不是距離精度、物體分類、道路穩定性
   或兩顆實體燈每次均有按記錄變化的驗收。

結論：現有資料**支持「觀測區有多個反射來源」**，與家具／牆壁假說相容；
但**尚未證實家具或牆壁是原因**。
