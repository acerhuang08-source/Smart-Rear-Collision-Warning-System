# BNO055 校正設定檔格式與安全生命週期

## 階段邊界

本功能最初只完成純軟體實作；該階段的測試使用 fake bus、fake clock 或暫存
目錄，當時沒有開啟實體 I²C，也尚未執行 confirmed CLI。後續已於 2026-09-12
在 Raspberry Pi 5 與 GY-BNO055 上完成本文所述的 profile export、真正斷電後
profile persistence、restore、立即 read-back、NDOF 品質及 calibration recovery
實機驗證。這項狀態演進不改寫最初 software-only 階段的歷史邊界。

本次實機範圍不包含外部姿態真值或角度精度、道路測試、實際騎乘、長時間可靠
性、TFMini Plus＋BNO055 sensor fusion、WarningPolicy 或正式 service 整合；這些
項目仍為 pending。

依 [Bosch BNO055 Datasheet Revision 1.8](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bno055-ds000.pdf)
第 3.6.4 與 4.3.85–4.3.106 節，page 0 的校正資料是連續 22 bytes：

| 暫存器 | 欄位 | 解碼與合法範圍 |
| --- | --- | --- |
| `0x55–0x5a` | accelerometer X/Y/Z offsets | little-endian signed 16-bit，各 `-500..500` LSB |
| `0x5b–0x60` | magnetometer X/Y/Z offsets | little-endian signed 16-bit，各 `-6400..6400` LSB |
| `0x61–0x66` | gyroscope X/Y/Z offsets | little-endian signed 16-bit，各 `-2000..2000` LSB |
| `0x67–0x68` | accelerometer radius | little-endian signed 16-bit，`-2048..2048` LSB |
| `0x69–0x6a` | magnetometer radius | little-endian 16-bit，`144..1280` LSB |

SIC matrix `0x43–0x54` 不屬於本階段。Profile restore 也不寫入
`AXIS_MAP_CONFIG` 或 `AXIS_MAP_SIGN`；它只讀取並比對 axis map，避免把一組安裝
方向的校正值套用到不相容設定。

## JSON schema version 1

Profile 是 deterministic UTF-8 JSON：key 排序、無非必要空白、檔尾一個 newline。
頂層只允許以下欄位，缺欄或多餘欄位都拒絕：

- `schema_name`：固定為 `rear-warning.bno055-calibration-profile`。
- `schema_version`：固定整數 `1`。
- `sensor_label`：操作者提供的非空白可列印標籤，最長 64 字元。
- `identity`：chip、accelerometer、magnetometer、gyroscope ID，以及 software／
  bootloader revision。
- `settings`：`UNIT_SEL`、power mode、目標 operation mode、讀取到的 axis-map
  config/sign；目前只支援專案既有 default units、normal power、NDOF。
- `calibration`：九個具名稱的 offset 與兩個 radius 整數欄位。
- `created_at_utc`：限定為 `YYYY-MM-DDTHH:MM:SS[.ffffff]Z`；小數秒可省略或
  使用 1–6 位。必須使用 calendar date、大寫 `T` 與大寫 `Z`，不接受 offset、
  week date、basic format、空格分隔、缺秒或不存在的日期／時間。
- `payload_sha256`：排除本欄後，對其餘 canonical JSON payload 計算的小寫
  64 字元 SHA-256。

設定檔不另外保存 22-byte blob，避免 blob 與解析欄位形成兩份真相。寫回前由
單一集中 codec 從具名稱欄位重新編碼；純函式 round trip 測試涵蓋正負值、
little-endian 邊界、所有欄位型別與資料表範圍。

Parser 拒絕 duplicate JSON key、NaN、infinity、非 UTF-8、過大輸入、bool、
float、string 冒充整數、非法 schema/version、固定 ID 錯誤、不支援設定、非法
axis permutation、時間格式錯誤與 hash mismatch。

## 安全檔案生命週期

實際 profile 必須明確指定路徑，建議放在專案外，例如：

```text
/home/topics/.local/state/rear-warning/bno055/
```

以下 atomic publication 保證只適用於目前實作與測試的 Linux／POSIX 語意，且
profile temporary 與 final 必須位於同一個支援 hard link、device/inode 身分與
directory `fsync` 的本機 filesystem。不宣稱網路 filesystem、FUSE、跨 filesystem
或其他平台具有相同的原子性與持久性保證。

發布流程如下：

1. 拒絕 symlink parent、已存在的 final path 及 final symlink。
2. 在相同目錄以不可預測名稱及 `O_EXCL` 建立唯一 temporary file。
3. 強制權限 `0600`，完成 write、flush、file `fsync` 及 close。
4. 以 hard link exclusive-create final path；final 已存在時絕不覆寫。
5. 核對 final 與 temporary 的 device/inode 身分相同後才移除 temporary。
6. `fsync` 目錄；若發布後步驟失敗，只在 inode 仍屬本次建立時回滾 final。
7. 失敗清理同樣只刪除本次記錄且重新核對身分的 temporary/final。

載入使用 `lstat`、`O_NOFOLLOW`（平台支援時）、open 後 `fstat` 身分比對及
64 KiB 上限；拒絕 symlink、目錄、裝置等特殊檔案、開啟期間被替換的檔案及
過大內容。所有 filesystem 操作與 temporary token 可注入測試；建立時間也由
CLI 可注入的 UTC clock 產生。

## Export 模式順序

```text
validate arguments
→ read and verify fixed identity IDs
→ existing CONFIGMODE/page 0/normal power/default units/NDOF initialization
→ bounded readiness polling
→ bounded CALIB_STAT polling (only raw 0xff succeeds)
→ CONFIGMODE + 19 ms
→ page 0
→ read units/power/axis map
→ read exactly 0x55–0x6a
→ decode/range-check/build/hash profile
→ CONFIGMODE cleanup + bus close
→ exclusive atomic profile publication
```

Calibration polling同時受 monotonic deadline 與
`ceil(timeout / interval) + 1` 最大嘗試次數限制，因此 constant／backward clock
或 no-op sleep 都必定結束。硬體讀取、模型驗證或 cleanup 任一步失敗都不發布
final profile。

## Restore 模式順序

```text
load + fully validate profile and sensor_label (before hardware adapter creation)
→ open bus
→ read and verify fixed identity and firmware revisions
→ CONFIGMODE + 19 ms
→ page 0 → normal power → default units
→ read and compare axis map
→ write each byte 0x55–0x6a in ascending order
→ block read 0x55–0x6a while still in CONFIGMODE
→ require byte-for-byte equality
→ NDOF + 7 ms
→ bounded mode/status/error readiness polling
→ bounded polling until one measurement passes the existing quality gate
→ CONFIGMODE cleanup + bus close
```

任一 byte write error 會指出 register；read-back mismatch 指出第一個不符的
register、expected 與 actual。Partial write、read-back、NDOF、readiness 或
measurement failure 都由 CLI 進入 cleanup。Primary 與 cleanup error 會分別
輸出；`device_cleanup_completed` 與 publication failure 時的
`profile_cleanup_completed` 分開標示。Ctrl+C 保留回傳 130，即使 profile cleanup
另有錯誤也不會誤報成功。只有完整流程與 device cleanup 成功才輸出
`restore_success`。

## 相容性與不可證明事項

BNO055 沒有本專案可驗證的唯一序號。固定 identity ID 只能辨識元件種類；
software/bootloader revision、`sensor_label` 和 SHA-256 也不能證明 profile 來自
同一顆實體 sensor。Profile 必須由操作者綁定目前模組、安裝方向與系統設定；
更換模組、移動安裝方向或變更 axis map 後不得直接假設相容。

`payload_sha256` 只是非密鑰完整性檢查，不提供來源認證、感測器身分證明或防止
惡意竄改。能修改 profile 的人也能修改內容後重新計算 hash；`sensor_label` 仍然
只是操作者提供的約束，不是可信的硬體身分。

`CALIB_STAT` level 3 只表示內部校正狀態，不是姿態精度保證。Restore 成功代表
profile 通過相容性檢查、22 bytes 寫回與立即 read-back 一致，並取得一筆通過
既有寬鬆品質 gate 的融合資料；不代表角度符合外部真值。BNO055 internal
calibration 在後續運作中仍可能更新 offsets/radius，因此 restore 成功也不代表
這些數值永久不變。

## 2026-09-12 實機驗證（PASS）

### 環境與 baseline

驗證使用 Raspberry Pi 5、I2C bus 1、address `0x29`，sensor label 為
`rear-imu-primary`。實機固定身分與設定如下：

| 欄位 | 實測值 |
| --- | --- |
| CHIP／ACC／MAG／GYR ID | `0xa0 / 0xfb / 0x32 / 0x0f` |
| Software／bootloader revision | `0x0308 / 0x15` |
| `ST_RESULT`／`SYS_ERR` | `0x0f / 0x00` |
| `AXIS_MAP_CONFIG`／`AXIS_MAP_SIGN` | `0x24 / 0x00` |

### Export 與磁碟 profile

Confirmed export 成功且 `device_cleanup_completed=true`。Profile 寫至專案外的
`/home/topics/.local/state/rear-warning/bno055/profile.json`，是 owner
`topics:topics`、mode `0600` 的一般檔案。驗證時整檔 SHA-256 為
`eb7b9c26c6a54f2b56d2dd0aeadec077d73b22817812e0b83c6cc6ff763085fc`，canonical
payload SHA-256 為
`dfb41f038bd4e0faa381086ce63b0813f1f36c8c02dfc150d705649023427aef`。

擷取的 `0x55–0x6a` 內容為：

```text
ff ff 02 00 05 00 f4 fa ab fa d3 f6 ff ff 02 00 02 00 e8 03 b6 02
```

解碼為 accelerometer offsets `(-1, 2, 5)`、magnetometer offsets
`(-1292, -1365, -2349)`、gyroscope offsets `(-1, 2, 2)`、accelerometer
radius `1000` 與 magnetometer radius `694`。Loader 重新驗證 schema、sensor
label、欄位範圍與 canonical checksum 均成功。Export 很快看到 full
`CALIB_STAT`；實機先前可能仍保有 offsets，因此這次結果不證明感測器是從完全
未校正狀態重新完成整套人工校正。

### 真正斷電與 restore

實體斷電再供電後，磁碟 profile 仍存在，mode、owner、整檔 SHA-256 與 canonical
payload SHA-256 均未改變。BNO055 calibration registers 則變成：

```text
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 e0 01
```

這項差異證明本次確實觀察到 volatile calibration data 因真正斷電而清除，而
磁碟 profile 保持完整。Confirmed restore 隨後回報：

```text
profile_validation_success
read_back_verified
measurement_verified
device_cleanup_completed=true
restore_success
```

Restore exit code 為 0；identity、firmware revision、sensor label 與 axis map
相容性檢查均通過，寫入後仍在 CONFIGMODE 執行的 immediate 22-byte read-back
與 profile 完全一致。NDOF 正常啟動，`SYS_STATUS=0x05`、`SYS_ERR=0x00`，且
quaternion／gravity 通過既有品質 gate。Cleanup 回到 page 0 CONFIGMODE，沒有
寫入 axis-map registers。

### Runtime calibration 與恢復

Immediate read-back 之後，進入 NDOF 的 BNO055 firmware 會動態調整 calibration
registers；實機曾觀察 magnetometer radius `694 → 0`、magnetometer offsets
改變及部分 gyroscope offsets 改變。因此驗收要求是寫入後的 immediate exact
read-back、NDOF readiness／measurement quality 與後續 calibration recovery，
不是要求 runtime registers 永久 byte-for-byte 固定。這項 firmware 行為本身
不構成 production bug 證據。

第一次 90 秒人工移動觀察取得 178 筆有效樣本，read、runtime-state 與
runtime-data errors 都是 0；mode/status/error 全程為 `0x0c/0x05/0x00`，所有
quaternion／gravity 正式樣本通過品質 gate。GYR 維持 level 3，MAG 依序出現
`0 → 1 → 0 → 1 → 2`，最後 calibration 為 `(3,3,1,2)`，故該輪記為
partial pass／recovery incomplete，不視為程式錯誤。

後續不重新 restore、export 或斷電，依序完成靜止、六個穩定方向與平順多方向
轉動。觀察取得 313 筆有效樣本、3 筆正常 startup discards，第一筆有效資料等待
0.090 秒，sampling elapsed 158.131 秒，平均 1.979 Hz；read、runtime-state 與
runtime-data errors 仍全為 0，正式樣本全部維持 `OPR_MODE=0x0c`、
`SYS_STATUS=0x05`、`SYS_ERR=0x00` 並通過 quaternion／gravity 品質 gate。

ACC 與 MAG 最終都恢復 level 3；首次完整 `(3,3,3,3)` 約在第一筆有效樣本後
141.24 秒出現，連續觀察約 14.19 秒，超過指定 10 秒門檻。達標後以 Ctrl+C
結束，因此 diagnostic exit code 130 是操作人員中斷，不是 hardware 或
diagnostic failure；`cleanup_completed=true`，結束後為 page 0 CONFIGMODE 且
`SYS_ERR=0x00`。額外等待 CLI 中斷送達期間曾看到 SYS level 再降為 0，但
GYR／ACC／MAG 仍為 3；本文不宣稱 calibration level 完成後會永久維持 3。

以上證據支持 BNO055 Calibration Profile hardware validation 為 PASS，但只限
profile 安全保存、真正斷電後持久性、相容性檢查、restore immediate read-back、
NDOF 啟動／品質、calibration recovery 與 cleanup。它不擴張到本節開頭列出的
道路、騎乘、外部姿態真值或系統整合項目。

## CLI 安全門檻

`export` 與 `restore` 都要求 `--bus`、`--address`、`--sensor-label`、明確的
profile path 及 `--confirm-hardware`。未確認時只列完整計畫並回傳 2：不開啟
profile、不建立檔案、不載入 `smbus2`、不建立 SMBus，也不做 register I/O。
工具不掃描目錄、不選取「最近」profile、不覆寫既有檔案，也不輸出 traceback。
