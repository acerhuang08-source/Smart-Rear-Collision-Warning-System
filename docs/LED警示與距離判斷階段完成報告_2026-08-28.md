# LED 警示與距離判斷階段完成報告

日期：2026-08-28

## 1. 階段目標

本階段完成 TFMini Plus 距離量測至三色 LED 警示的軟體資料鏈，保留原始距離進入門檻，並加入獨立、可設定且不執行 I/O 的狀態遲滯。階段收尾包含既有實作審查、軟體測試、文件狀態確認與安全失效行為驗證。

本報告只宣告軟體階段完成。既有實體測試是加入 hysteresis 前的歷史基準；目前 hysteresis 尚未完成實體硬體驗證。

## 3. 分層資料流

```text
TFMiniPlusSerialDevice
  -> TFMiniPlusParser
  -> TFMiniPlusMeasurement
  -> WarningPolicy
  -> WarningStateStabilizer
  -> WarningController
  -> LedDriver
  -> ThreeColorLedDriver
  -> DigitalOutput adapter
```

UART 裝置、封包解析、無狀態距離分類、有狀態遲滯、應用協調及 LED 輸出各自位於不同模組。核心判斷不依賴 GUI、UART、GPIO 或實體硬體。

## 4. 距離進入門檻

原始 `WarningPolicy` 進入門檻維持不變：

| 距離 | Policy 分類 |
| --- | --- |
| `0 < distance < 1.5 m` | `DANGER` |
| `1.5 m <= distance <= 3.0 m` | `WARNING` |
| `3.0 m < distance <= 12.0 m` | `SAFE` |
| 缺失、非數值、非有限值、零、負值或超過 12.0 m | `SENSOR_FAULT` |

## 5. Hysteresis 解除門檻

預設解除門檻是 `danger_release_m=1.7` 與 `safe_release_m=3.2`：

- `DANGER` 在小於 1.7 m 時維持 `DANGER`。
- `DANGER` 在 1.7 m 至 3.2 m（含端點）轉為 `WARNING`。
- `DANGER` 只有在大於 3.2 m 時可直接轉為 `SAFE`。
- `WARNING` 在不大於 3.2 m 時維持 `WARNING`，大於 3.2 m 才轉為 `SAFE`。
- `SAFE` 或 `WARNING` 收到小於 1.5 m 時立即進入 `DANGER`。
- 無效量測從任何狀態立即進入 `SENSOR_FAULT`。
- 從 `SENSOR_FAULT` 恢復時，第一筆有效量測直接採用原始 policy 分類。

收尾審查另以純軟體方式確認 1.69、1.70、3.01、3.20、3.21 與 1.49 m 等指定邊界案例。兩個 0.2 m release margin 是初始、可調整值，不是完成實機調校後的定值。

## 6. LED 狀態對應

| 狀態 | LED |
| --- | --- |
| `SAFE` | 綠燈 |
| `WARNING` | 黃燈 |
| `DANGER` | 紅燈 |
| `SENSOR_FAULT` | 紅燈與黃燈 |

預設腳位維持紅燈 BCM 17、黃燈 BCM 27、綠燈 BCM 22。本階段收尾沒有修改腳位或操作 GPIO。

## 7. 啟動與 SENSOR_FAULT 安全行為

診斷 session 的初始邏輯狀態為 `SENSOR_FAULT`，但在第一筆讀取前會先讓三顆 LED 保持全關，避免尚無有效量測時誤示為安全。第一筆 empty read 才顯示紅燈與黃燈；第一筆有效量測則直接使用 policy 分類的穩定後狀態顯示對應 LED。

缺失、無效或超出範圍的量測均以 fail-safe 方式顯示 `SENSOR_FAULT`，不會當成 `SAFE`。從故障恢復後的第一筆有效資料不受 release threshold 延遲。

## 8. Controller、Pipeline 與 CLI 整合結果

- 每個 `WarningController` 自行建立或接收一個 stabilizer，不與其他 controller 共用狀態。
- Controller 不保存第二份警示狀態；狀態所有權位於 stabilizer。
- 注入 stabilizer 的 entry thresholds 必須等於 policy thresholds，且不相容設定會在 LED I/O 前被拒絕。
- 每筆 measurement 經 policy 分類後只呼叫一次 `stabilize()`，其回傳值同時作為 controller 回傳值及 LED 輸入。
- Pipeline 回傳 controller 的穩定後狀態；CLI 的狀態計數、最終狀態及 transition count 使用同一狀態。
- CLI 只有在狀態實際改變時增加 transition count；重複狀態不增加轉換次數。
- CLI 顯示實際使用的 entry thresholds、release thresholds，以及由兩者相減得到的 `hysteresis_margin_m`。
- CLI 明確顯示 `distance_filtering=disabled`，且顯示設定與建立 controller 時使用同一組設定物件。

## 9. 設定驗證與測試範圍

`HysteresisThresholds` 的 intrinsic validation 涵蓋兩個欄位的 bool、string、NaN、正負 infinity 與負值，並拒絕 danger release 大於 safe release。這些檢查在設定物件建構時執行，不依賴後續 policy 相容性錯誤。

獨立的 policy-relative validation 涵蓋：

- danger release 低於 danger entry；
- safe release 低於 warning／safe boundary；
- safe release 大於或等於最大有效距離；
- 自訂 release 與 entry thresholds 不相容。

測試也涵蓋原始 policy 邊界、hysteresis 狀態轉換、即時危險升級、故障與恢復、controller 狀態隔離、pipeline 跨 poll 狀態、LED pattern、啟動全關、首次 empty read、CLI 設定顯示與穩定後統計。所有測試使用 fake 或純軟體資料，未存取實體 UART 或 GPIO。

## 11. 既有 pre-hysteresis 實體測試摘要

2026-08-24 的歷史 30 分鐘實體 UART-to-LED 整合測試共記錄 176,609 筆有效量測，平均 98.110 Hz，`empty_reads=0`、`parser_errors=0`、`sensor_faults=0`，且 cleanup 成功。既有 10 秒與 30 分鐘結果均為 **pre-hysteresis historical baselines**，數據未在本階段修改或回溯重算。

這些歷史結果證明當時的 TFMini Plus、parser、policy、controller、gpiozero/lgpio adapter 與 LED 警示鏈可以完成整合運作，但不包含目前 hysteresis 行為。

## 12. Current-hysteresis 實體驗證狀態

> **Hysteresis status: physical validation pending.**

目前 hysteresis 只有完整的軟體與 fake-boundary 驗證，尚未在 Raspberry Pi 5、TFMini Plus 與實體 LED 上執行 current-hysteresis 邊界切換、長時間穩定性或 release margin 調校。因此不得把本階段描述成已完成所有實體驗證。

## 13. Distance filtering 狀態

> **Distance filtering: disabled.**

目前沒有啟用 moving average、median filter 或其他距離濾波。現有 0.2 m release margin 為 initial/tunable 值；hysteresis 降低狀態邊界往返切換，但不等同於距離濾波。

## 14. 後續建議

1. 經使用者確認硬體影響與 UART ownership 後，另行規劃 current-hysteresis 實體邊界測試。
2. 在 1.5／1.7 m 與 3.0／3.2 m 附近記錄原始距離、policy candidate、穩定後狀態及 LED 狀態。
3. 以實測雜訊、轉換頻率及反應延遲評估 0.2 m margin 是否需要調整。
4. 先定義延遲、安全失效與評估指標，再決定是否另案加入 distance filtering。
5. 保留 pre-hysteresis 歷史資料，不以新策略回溯改寫既有結果。
