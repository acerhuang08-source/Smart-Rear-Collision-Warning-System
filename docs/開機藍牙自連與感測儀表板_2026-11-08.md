## A. MOTO A2 Plus 開機自連

### 現地盤點與設計

- BlueZ 5.82、PipeWire 1.4.2、WirePlumber 0.5.8；沒有升級或安裝另一套音訊系統。
- `topics` linger 在變更前已為 yes，PipeWire、pipewire-pulse、WirePlumber 均 enabled/active。
- BlueZ `bluetooth.service` enabled/active；`main.conf` 使用 `AutoEnable=true` 預設，adapter 當時 powered=yes。
- WirePlumber 一般 `main` profile 會 wants `monitor.bluez.seat-monitoring`；只有 systemwide mixin 預設 disabled。
  因此安裝 `topics` 專用 fragment，只關閉其 Bluetooth seat monitoring。這使無桌面 session 也能
  建立 node，但若同機有其他圖形使用者，可能出現藍牙音訊所有權競爭。
- 現地原本沒有專案 MOTO autoconnect unit。新增的單一管理者不掃描、不配對、不清除其他裝置；
  已就緒時不 connect。未就緒才對私有設定的 paired/trusted/name-matched 裝置發出一次
  有期限 `connect`，並另行要求恰一個屬於該身分的 `Audio/Sink`。
- sink 每輪從 BlueZ address properties／node identity 動態辨識，不使用歷史 `object.serial=79`、wpctl ID
  或私有設定內的舊 target node 來宣告就緒。版控 unit／fragment 不含 MAC 或含 MAC 的 node。
- 服務狀態行含 boot-relative monotonic seconds，追加至被 `.gitignore` 排除的
  `local-state/moto-autoconnect.log`，供登入後查驗是否早於 SSH／桌面 session。

關聯檔案：

- `src/rear_warning/voice/autoconnect.py`
- `config/systemd/user/rear-warning-moto-autoconnect.service`
- `config/wireplumber/91-rear-warning-headless-bluetooth.conf`
- 安裝前狀態：`local-state/moto-autoconnect-preinstall-20261108/STATE.txt`（忽略、不進版控）

### 安裝／啟用

`loginctl show-user topics -p Linger` 若不是 `yes`，才執行 `loginctl enable-linger topics`。本機原本已是 yes，
本輪沒有改 linger。

```bash
cd /home/topics/Projects/Smart-Rear-Collision-Warning-System
install -d -m 0700 /home/topics/.config/systemd/user
install -d -m 0700 /home/topics/.config/wireplumber/wireplumber.conf.d
install -m 0644 config/systemd/user/rear-warning-moto-autoconnect.service \
  /home/topics/.config/systemd/user/rear-warning-moto-autoconnect.service
install -m 0644 config/wireplumber/91-rear-warning-headless-bluetooth.conf \
  /home/topics/.config/wireplumber/wireplumber.conf.d/91-rear-warning-headless-bluetooth.conf
systemctl --user daemon-reload
systemctl --user restart wireplumber.service
systemctl --user enable --now rear-warning-moto-autoconnect.service
```

`restart wireplumber` 會短暫中斷 `topics` 的音訊 node；不重啟 BlueZ。

### A 開機驗收結果

1. **情境一／耳機先開：通過。**操作員正常重開 Pi，未手動 connect，也未手動啟動
   音訊服務。`topics` 因 linger 於開機約 6.825 秒啟動 user manager；自連 unit 由
   `default.target` wanted，於 8.745 秒啟動，local log 於 9.152 秒記錄 BlueZ connected 且唯一
   `Audio/Sink` 就緒。第一個遠端登入為 31.113 秒，因此可排除 SSH 觸發。
2. 本次 boot 的 Wayland session 於 8.366 秒已存在，音訊就緒為 9.152 秒。unit 的
   `WantedBy=default.target`、linger=yes 及 topics-only seat-monitoring override 證明它不依賴 SSH
   手動啟動；但本次沒有一個「從 boot 到就緒全程無 Wayland」的直接實景，不把它冒稱為
   額外的純無桌面 boot 驗收。
3. **情境二／Pi 先開、耳機後開：通過。**操作員關閉耳機後，唯讀狀態為
   `connected=false`、sink=0、`device_disconnected`。一般開機且不進配對模式後，
   服務 log 從 monotonic 789.153 秒的 disconnected 轉為 819.154 秒的 `audio_ready`，
   實際差值 **30.001 秒**，在本輪 90 秒觀察窗內。首筆外部查證時已 ready，不把查詢時差假稱為
   0 秒連線。
4. 兩情境均同時核對 BlueZ connected 及唯一 MOTO `Audio/Sink`；服務 `NRestarts=0`、
   `Discovering=no`。全程沒有掃描、手動 connect、播放、改音量或啟動感測器。

## B. 中文瀏覽器即時感測儀表板

### 架構與邊界

- `rear_warning.dashboard` 只讀取現行 SHADOW capture；Web client 與 HTTP server 都不開 UART／I²C。
- SHADOW 仍是單一採集者；只將 `shadow.jsonl` 與 `bno055.jsonl` 設為逐行可見，並在
  additive schema 保存全部 selector candidates。parser、UART、BNO 取樣、融合與警示門檻不變。
- 背景 source 每 0.25 秒讀取新 JSONL，保留最多 120 個距離點。HTTP client 只讀同一 snapshot，
  多分頁不增加 sensor reader 或改變取樣率。前端 2 Hz polling，每次 1.5 秒 timeout。
- 來源分為 not_started／historical／live／stale／stopped／error。age 只在 server 親眼看到本 boot
  新資料後以來源 monotonic timestamp 計算；舊 capture 不用 HTTP 時間假裝即時。
- run 切換、檔案替換／截斷時清空舊目標與歷程。零目標保留 null 與原因，不補 0。
- BNO 分開「一般資料完整性」「四項完整校正」「profile loaded」。現行 SHADOW 沒有保存角速度，
  畫面明示「—／現行 SHADOW 未保存角速度」。
- X／Y／Vx 顯示原單位與「軸向未確認」；Vx 不命名為接近速度或車速。距離 warning 只稱候選，
  不表示 GPIO／LED／語音已啟用。
- 耳機欄只做 read-only status，不 connect／play；API 不輸出 MAC 或 node name。

### 手動啟動 Web

```bash
cd /home/topics/Projects/Smart-Rear-Collision-Warning-System
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python \
  -m rear_warning.cli.dashboard \
  --capture-root shadow-results --source LIVE \
  --host 127.0.0.1 --port 8765 \
  --voice-config config/voice-alert.local.toml
```

Pi 本機 URL：`http://127.0.0.1:8765/`。只綁 loopback；CLI 會拒絕非 loopback host。

專案文件內找不到 Windows 既有 SSH alias 的可驗證名稱，因此不臆造。在 Windows 使用者現有 alias：

```powershell
ssh -N -L 8765:127.0.0.1:8765 <既有-SSH-alias>
```

然後開啟 `http://127.0.0.1:8765/`。

### A 兩個功能情境通過後的真實畫面驗收

啟動 Web 不會啟動採集。另一個互動終端先查 owner：

```bash
fuser -v /dev/ttyAMA0 /dev/i2c-1
systemctl show tfmini.service -p ActiveState -p MainPID
```

若有任何未知 owner 就停止，不 kill、不從網頁停 service。確認裝置、接線、供電與 owner 後，
手動執行現地真實 SHADOW 入口：

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python \
  -m rear_warning.cli.ioradar701_shadow live \
  --port /dev/ttyAMA0 --baudrate 230400 \
  --i2c-bus 1 --bno055-address 0x29 \
  --motion-period 0.1 --maximum-motion-age 0.2 \
  --duration 60 --confirm-hardware --plain
```

命令先列計畫並等操作員 Enter；Enter 後會獨佔 ttyAMA0、230400／8N1／無流控／只收，
佔用 I²C bus 1 address 0x29，並將 BNO055 切入 NDOF。不送雷達命令，不建立 GPIO／LED／語音 adapter。
Ctrl+C 會走現行 cleanup。驗收只核對網頁數值更新、來源時間／單位、採集停止後失效及資源收尾；
不宣告距離精度、完整校正、共同車體融合或道路警示通過。

實際驗收結果：

- 操作員先手動停止已知的 `tfmini.service`，唯讀 preflight 確認
  `/dev/ttyAMA0` 與 `/dev/i2c-1` 無 owner；Codex 沒有 kill 程序或自動停服務。
- 儀表板只綁定 `127.0.0.1:8765`，`/healthz` 回 `ok`。操作員以 Windows SSH
  local forwarding 開啟網頁，之後由 SHADOW 互動門檻手動按 Enter 開始 60 秒。
- Pi 現地時鐘產生的 run ID 為 `live-20261101T123449.630960+0800`；這個目錄日期與
  本任務的 2026-11-08 用戶日期不同，故保留原 run ID 並不倒推為其他實驗。
- 採集中 API 為 `source_state=live`，radar/BNO age 實際抽查約 0.20／0.28 秒；
  同時顯示真實目標、零目標原因、BNO 姿態／四元數／加速度／校正狀態。
  零目標沒有補 0，未完整校正沒有冒稱完整校正。
- 操作員確認採集中雷達／BNO 數值與圖表持續更新；採集結束後網頁
  顯示來源已停止，不是「即時」。API 同時為 `source_state=stopped`、
  `source_reason=來源採集已停止`，radar/BNO age 均為 null。
- summary：30,036 raw bytes、2,503 decoded frames、552 BNO records、1,192 SHADOW records、
  928 fusion updates；checksum failure、sync discard、trailing bytes、radar time discontinuity、
  errors 與 cleanup errors 全為 0。`recording_complete=true`、`interrupted=false`。
- 結束後 UART／I²C 無 owner，儀表板也已以 Ctrl+C 停止且 8765 無 listener。
  依操作員要求，`tfmini.service` 保持 inactive，沒有自動恢復；語音保持
  `enabled=false`。
