# 手動開始 LIVE 偵測

在樹莓派本機、SSH（需配置 TTY）或 VS Code 終端機，複製以下整條命令：

```bash
cd /home/topics/Projects/Smart-Rear-Collision-Warning-System && PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python -m rear_warning.cli.live_detection --port /dev/ttyAMA0 --baudrate 115200 --i2c-bus 1 --bno055-address 0x29 --confirm-hardware
```

這些裝置參數來自現行 `sensor-sync-diagnostic` 設定及既有實測文件。本輪開發
環境未提供 `/dev/ttyAMA0`、`/dev/i2c-1`，所以沒有重新驗證當下硬體接線或位址。
若你的模組／裝置路徑已更換，先依實際接線修改命令中的參數。

## 開始與停止

1. 固定感測器與目標，確認供電、UART／I²C 接線，及兩個裝置沒有其他程式使用。
2. 執行命令後會列出 UART、鮑率、timeout、I²C bus/address、刷新率及預計的
   BNO055 模式切換，接著顯示「按 Enter 開始偵測，Ctrl+C 離開」。這時尚未
   建立 UART／SMBus adapter，也未開始感測。
3. 按空白 Enter。程式檢查裝置及占用者、開啟 UART、驗證 BNO055 identity，
   依既有 device layer 寫入 CONFIGMODE／page 0／normal power／SI units／NDOF。
   通過 readiness 與品質檢查後開始採集及融合判斷。先保持平台及目標穩定，
   等待資料視窗與近期基準累積；實際 `UNCERTAIN` 是合法結果。
4. 支援 ANSI 的終端機每秒約 5 次原位更新中文面板；最近事件留在面板底部。
5. 按 Ctrl+C。程式關閉本次 UART，讓 BNO055 回 CONFIGMODE 並關閉 I²C bus，
   最後列出統計及 `cleanup_completed`。使用者中止回傳 130；cleanup 失敗回傳 1。
6. 再次執行同一命令可開始全新一輪，重新建立基準。

`--confirm-hardware` 加上互動 Enter 才能啟動。`--help`、參數錯誤、EOF、輸入其他
文字或 Ctrl+C 都不會啟動硬體。第一版要求 stdin、stdout 都是 TTY；不接受
`echo | ...`、輸出重導或 pipe 自動啟動，可使用終端機複製文字／錄影留存。
本入口沒有 SIM fallback、LED 控制、服務管理或校正檔操作。

## 固定面板與純文字

原命令不用加參數即可顯示面板。按 Enter 前仍為設定與開始提示，之後顯示
初始化、暖機及當下資料。面板使用替代畫面，Ctrl+C／異常結束時恢復一般
畫面、游標、色彩與原 fd blocking 設定，留下逐項短行摘要及完整錯誤。

- 要複製連續資料行，在原命令末尾加 `--plain`。`TERM=dumb` 自動用純文字；
  顯示層對非 TTY 也不產生 ANSI，但 CLI 仍保留原有 stdin/stdout TTY 啟動門檻，
  不因這個選項開放 pipe 自動啟動。
- 80×24 使用雙欄，窄視窗改單欄及最多一筆最近事件；寬版最多三筆。
  長原因按中文顯示寬度換行，不截斷。若必要內容無法完整放入視窗，提示後
  本輪持續使用純文字，避免因錯誤長度或反覆縮放一直切換畫面；重啟可回面板。
- 「判斷狀態」「最近確認分類」「待確認候選」「原因」分開顯示。
  待確認期間保留的分類不是新 ready 結果；缺值不以零補上。過期時隱藏舊數值，
  顯示「失效／不確定」及原因，不能把舊分類當最新結果。
- 暖機／待定為黃色，失效為紅色；正常文字沿用預設前景色。
  `NO_COLOR=1` 可關閉色彩，文字語意相同。「未達條件」不等於確定靜止，
  「距離穩定或遠離」不代表安全，「符合目標接近判定條件」不代表已確認碰撞。
- 主要面板省略 enum／reason code／原始樣本年齡；這些仍在 `--plain` 詳細行。
  有效資料年齡不是畫面刷新年齡。顯示丟棄是合併或來不及輸出的畫面／事件，
  不是採樣或推理丟失。事件保留原始時間及順序。

## 欄位解讀

| 欄位 | 意義 |
| --- | --- |
| `LIVE 實際感測` | 此入口讀取實體感測器；錯誤不會切換成模擬資料 |
| `t` | Enter 後經過時間，包含初始化；摘要另列正式採集時間 |
| 樣本年齡 | 目前主機 monotonic 時間減距離 canonical timestamp |
| 有效距離／動作年齡 | 最近通過驗證的兩種輸入各自的年齡；不是顯示刷新的時間 |
| 距離 | 公尺；無效數值顯示「無效」，斷流後顯示「資料不足」 |
| 接近率 | 沿感測方向的距離變化，m/s；趨勢未 ready 或當筆距離無效時顯示「資料不足」 |
| 平移／旋轉 | 短窗動作證據是否達條件；「未達條件」不等於確定靜止 |
| 分類 | 公開 assessment 的繁中名稱及 enum，原有持續條件不變 |
| 基準 | 公開 `stationary_baseline_ready`；失效／恢復時須重新累積 |
| 健康 | `matched`、stale、future、invalid 或距離斷流；暖機／待定與原因另列 |
| 候選 | 正在等待 persistence 的候選分類，不能當成已提交分類 |
| 丟棄顯示 | 被合併／過期的狀態行及溢位的歷史事件數；不代表丟棄推理樣本 |

分類仍為 `STABLE_OR_RECEDING`、`STATIC_OR_SELF_APPROACH`、`TARGET_APPROACH`、
`UNCERTAIN`。它們不表示道路安全、車種或絕對車速。沒有近期靜止基準的接近
會維持不確定；目標接近不能超過基準有效期。

`--plain` 輸出形狀示例（縮寫，非本輪實機紀錄；實際結束摘要逐項換行）：

```text
按 Enter 開始偵測，Ctrl+C 離開
[LIVE 實際感測] 初始化 UART／BNO055 NDOF…
[LIVE 實際感測 t=0.20s] 樣本年齡=0.000s ... 距離=4.00m 接近率=資料不足 ... 分類=資料不足或情況不確定 (UNCERTAIN) 基準=不足 ...
[LIVE 實際感測 t=1.40s] ... 距離=4.00m 接近率=0.00m/s 平移=未達條件 旋轉=未達條件 ... 基準=成立 健康=matched ...
[LIVE 結束] total_elapsed=... sampling_elapsed=... valid_distance_measurements=... valid_motion_total=... interrupted=true cleanup_completed=true ... exit_code=130
```

## 刷新、斷流與時間限制

加上 `--refresh-hz 2` 可降低文字刷新；範圍為大於 0、至多 20 Hz。每筆量測仍經
原有 coordinator、causal matching 與 adapter，canonical timestamps 不受刷新率
影響；motion sample 重用不增加唯一動作樣本數。BNO055 間隔保持 0.1 秒、配對
最大 age 0.2 秒，所有 fusion 預設閾值保持原值。

UART timeout 預設 0.02 秒，最多 0.1 秒。空讀時 coordinator 仍週期呼叫健康檢查；
距離最後一筆超過 0.25 秒即顯示「資料斷流／過期」、`UNCERTAIN`、基準不可用，
不再呈現舊數值為最新結果。這是顯示有效期，不會偽造量測送進 classifier；
資料恢復後 adapter 仍依自己的時間間隔規則清除不連續的推理狀態。

採集 callback 不等待終端機：Linux 非阻塞寫入只保留最新狀態、最多 16 個待送
事件／控制訊息與一筆已部分輸出的文字，記錄合併／丟棄數。面板另保留最多
三筆最近事件，不另外開輸出執行緒。尚未開始傳送的過期狀態會丟棄。
事件均標示為歷史轉換並附事件時間；SSH 已送入作業系統緩衝的位元組仍可能延遲。
完整一筆輸出持續 2 秒不能送出即結束採集並 cleanup；終端機斷開也會觸發清理。

正常模式持續到 Ctrl+C；可加 `--duration 30` 在 BNO055 data-ready 後採集 30 秒
自動結束。既有 bounded diagnostic 入口不變；interactive coordinator 仍對停滯
時鐘設定 iteration guard，沒有無限錯誤重試。

BNO055 readiness／data-ready 皆沿用 2 秒有限輪詢。LIVE 主執行緒另以 5 秒
SIGALRM watchdog 限制沒有採集進度的操作，並對每個 cleanup 重新給予 5 秒。
不更改系統 I²C timeout 或驅動設定；Python signal 無法保證中止核心層不可中斷的
driver hang，實機最長 I²C 延遲仍待量測。SIGTERM／SIGHUP 也走中止與 cleanup；
作業系統強制終止（SIGKILL）或斷電無法由程式執行 cleanup。

## 常見錯誤

- **裝置忙碌**：啟動前以唯讀 `fuser` 檢查 UART／I²C owner；UART 再使用
  pySerial exclusive lock 與 Linux TIOCEXCL。若其他程序（例如原有採集服務）
  正在使用，會回報 PID 並停止，不會終止程序或操作 systemd。請由操作員先
  協調釋放裝置。跨帳號或受隱藏的程序可能無法完整查到，仍需操作員確認。
- **裝置不存在／權限不足**：核對命令的裝置路徑、bus、登入帳號的 dialout／i2c
  權限；不自動執行 sudo 或改系統設定。
- **缺少 fuser／smbus2／serial**：會回報缺少工具／依賴並停止；沿用原專案 `.venv`
  與已安裝的硬體依賴，本輪沒有新增安裝。`--help` 不需要載入硬體套件。
- **無資料／stale**：確認供電、對準方向、鮑率與裝置是否真的回傳資料；過期值
  不會繼續顯示成有效判斷。無資料不等於已確認拔線。
- **初始化／讀取失敗**：保留 exception cause chain，包括底層權限／通訊原因；
  結束後核對 cleanup 狀態，失敗時不可宣稱設備已正常釋放。
- **輸出中斷**：先清理硬體，再嘗試在 stderr 回報摘要；若終端機完全斷線，
  該連線自然無法接收摘要。

## 操作員短測與紀錄（本輪待實機驗證）

1. 執行命令並停在 Enter 提示，確認尚未開始採集。
2. 按 Enter，固定平台與目標等待 warmup、基準與健康狀態；記錄實際數值。
3. 沿感測方向移動紙板／模型車，再在可控場地移動平台，保留實際分類與原因，
   即使是 `UNCERTAIN` 也如實記錄，不調低門檻。
4. Ctrl+C，記錄摘要與 `cleanup_completed`；再次執行，確認裝置可重新使用。

記錄日期、HEAD／dirty、完整參數、觀察與兩輪 cleanup 結果。不要通電拔接線
作為故障展示；短測不等於道路、精度或全情境融合驗證。
